# Design

## Context

See proposal.md (Why) for the motivation. Current state of the code:

- Both projects target `net6.0` and there is no `global.json`.
- `Program.cs` calls `UseSqlServer` with `ConnectionStrings:DefaultConnection`, runs `DataSeeder` synchronously before `app.Run()`, and ends with `public partial class Program { }` so that `WebApplicationFactory<Program>` can find it.
- `SomethingFactory` builds a raw `mcr.microsoft.com/mssql/server:2022-latest` container with the Testcontainers 2.x generic builder. It binds host port 1433 to container port 1433, sets the deprecated `SA_PASSWORD` variable and hard-codes the connection string. It replaces the `DbContextOptions<ApplicationDbContext>` registration in `ConfigureTestServices`. A `#pragma` is needed because `IAsyncLifetime.DisposeAsync()` (xUnit v2, returns `Task`) clashes with `WebApplicationFactory.DisposeAsync()` (returns `ValueTask`).
- The migration snapshot was generated by EF Core 6.0.7 (`ProductVersion`).
- No code references FluentAssertions, NSubstitute or EF Core Sqlite.

## Goals / Non-Goals

**Goals:**
- Make one jump from 6 to 10 and keep the solution building and testing green at each task-group boundary.
- Remove the integration tests' dependency on the host machine (port 1433, a hard-coded password in the test code).

**Non-Goals:**
- Moving to Central Package Management (`Directory.Packages.props`). It can be a follow-up; this solution only has two projects.
- Upgrading the client-side libraries in `wwwroot/lib` (Bootstrap, jQuery).
- Moving secrets out of `appsettings.json`, adding CI pipelines or a Dockerfile, or making `DataSeeder` idempotent.
- Opting into the Identity schema version 3 (passkeys) tables introduced in .NET 10.

## Decisions

### D1: Go straight to net10.0 rather than stepping through 8 and 9
Neither project depends on anything that changed in an intermediate release in a way that needs staged migration. Stepping through 8 and 9 would add three rounds of package bumps with no extra safety, because the compiler, the EF migration check and the integration test catch the same problems either way. *Alternative:* 6 → 8 → 10, rejected as extra work for no gain.

### D2: Pin the SDK with `global.json`
Use `"version": "10.0.100", "rollForward": "latestFeature"` so any 10.0.x SDK works but a 9.x or 11.x preview SDK does not. *Alternative:* no pin, rejected because the build would depend on whichever SDK happens to be installed.

### D3: Use the Testcontainers.MsSql module
`MsSqlBuilder` handles the EULA, `MSSQL_SA_PASSWORD`, the wait strategy and a random host port, and `GetConnectionString()` returns a working connection string with `TrustServerCertificate=True`. This satisfies the integration-test-harness requirements "Isolated database per test run" and "No fixed host port". Pin the image explicitly (`mcr.microsoft.com/mssql/server:2022-latest`) so the module's default image cannot change underneath us. *Alternative:* keep the generic `ContainerBuilder` with a random port, rejected because it means reimplementing what the module already does.

### D4: Point the app at the container through configuration, not by replacing the DbContext registration
From EF Core 9, `AddDbContext` also registers `IDbContextOptionsConfiguration<T>`. Removing only `DbContextOptions<T>` therefore leaves the original `UseSqlServer(appsettings)` configuration in place, and the second `AddDbContext` stacks on top of it. Instead, override `ConnectionStrings:DefaultConnection` with `builder.UseSetting(...)` in `ConfigureWebHost`, so `Program.cs` reads the container's connection string as usual. *Fallback:* if `UseSetting` is applied too late for the minimal-hosting `builder.Configuration` read, use `services.RemoveAll<IDbContextOptionsConfiguration<ApplicationDbContext>>()` and `services.RemoveAll<DbContextOptions<ApplicationDbContext>>()`, then `AddDbContext` again.

### D5: Use xUnit v3 rather than staying on v2
xUnit v2 is in maintenance only. In v3, `IAsyncLifetime` extends `IAsyncDisposable` and its methods return `ValueTask`, which lines up with `WebApplicationFactory.DisposeAsync()`. That lets the factory `override` `DisposeAsync` (stop the container, then call `base.DisposeAsync()`) and the `#pragma` can be deleted. Migration steps: switch the package to `xunit.v3`, add `<OutputType>Exe</OutputType>`, change `using Xunit.Abstractions` to `using Xunit`, and switch `ValueTask`s.

*Found during implementation:* `xunit.v3` 4.x runs on Microsoft Testing Platform by default, and on the .NET 10 SDK `dotnet test` refuses to run an MTP project through VSTest. Use the `xunit.v3.mtp-off` package instead: it is the same xUnit v3 framework, run through VSTest, so `Microsoft.NET.Test.Sdk`, `xunit.runner.visualstudio` and `coverlet.collector` keep working without changes. Moving to MTP (a `"test": { "runner": "Microsoft.Testing.Platform" }` entry in `global.json` and an MTP coverage extension) can be a follow-up. *Alternative:* `xunit` 2.9.3 with the newest runner that still supports v2, rejected because v2 will not get new features.

### D6: Use AwesomeAssertions instead of FluentAssertions 8
FluentAssertions 8.0 and later require a paid Xceed licence for commercial use. AwesomeAssertions is a community fork under Apache-2.0 with a matching API (namespace `AwesomeAssertions`). Use it to replace `Assert.True(true)` with assertions on the returned user. *Alternatives:* pin FluentAssertions 7.x (the last free version, which will not get further updates), or use plain xUnit `Assert` and drop the package.

### D7: Fix the connection string for SqlClient TLS defaults
EF Core 7 and later bring Microsoft.Data.SqlClient 5+, which defaults to `Encrypt=True`. A local SQL Server with a self-signed certificate then fails the TLS handshake. Add `TrustServerCertificate=True` to the development connection string in `appsettings.json`. The test path already gets this from D3.

### D8: Drop the redundant `public partial class Program { }`
.NET 10 generates a public `Program` partial for top-level-statement apps, and analyzer ASP0027 flags the explicit declaration as unnecessary. Remove it and confirm `WebApplicationFactory<Program>` still compiles.

### D9: Bring migrations in line with EF Core 10
From EF Core 9, `Migrate()` throws if the model differs from the latest snapshot (`PendingModelChangesWarning`). After the upgrade, run `dotnet ef migrations has-pending-model-changes`. If it reports changes, for example from Identity 10 model defaults, add a migration (`UpgradeToNet10`) rather than editing `InitialCreate`, so existing databases can upgrade in place. If it reports none, keep the existing migrations; EF updates the snapshot's `ProductVersion` the next time a migration is added.
### D10: Remove unused packages instead of upgrading them
No code uses `Microsoft.EntityFrameworkCore.Sqlite` (the app only calls `UseSqlServer`) or `NSubstitute` (the tests use no mocks). Upgrading them would mean extra restore work, more transitive dependencies and more vulnerability surface for no benefit. Remove both references, and add them back if a future change needs SQLite or mocking. *Alternative:* upgrade both to their latest versions, rejected because they would be dead dependencies.

### D11: Pin patched NuGet client packages
*Found during implementation:* `Microsoft.VisualStudio.Web.CodeGeneration.Design` 10.0.2, the latest version, still depends on `NuGet.Packaging`/`NuGet.Protocol` 6.12.1, which have a known low-severity vulnerability (GHSA-g4vj-cjjj-v7hg). That fails the "no vulnerable packages" check. Add direct references to the patched 6.12.5 versions in the app project. Remove them once a newer CodeGeneration.Design pulls in a fixed version. *Alternative:* drop CodeGeneration.Design (it is only used for `dotnet aspnet-codegenerator` scaffolding), rejected because the request was to keep and upgrade packages, not remove tooling.

## Risks / Trade-offs

- [Identity 10 changes the schema, so the new migration alters existing tables] → Review the generated migration before committing it, and confirm it only touches the Identity tables in ways that keep existing data.
- [`UseSetting` override is ignored by minimal hosting] → Use the D4 fallback; the integration test fails loudly if the app connects to the wrong server.
- [xUnit v3 runs tests out of process as an exe, which can change how IDE test runners discover them] → Confirm discovery with `dotnet test --list-tests`. Visual Studio 2022 17.14+ and Rider 2025.1+ support v3.
- [The `2022-latest` SQL Server image is a moving tag] → Accepted, as it is today. Pin a CU tag later if image changes cause flaky tests.
- [Running the tests needs Docker and pulls an image of about 1.5 GB] → Unchanged from today; document it as a prerequisite.

## Migration Plan

All work happens on a branch and is merged once `dotnet build` and `dotnet test` pass on .NET 10. To roll back, revert the merge. The only lasting state change is an optional new EF migration; if one was added and applied to a real database, roll back with `dotnet ef database update InitialCreate`.
